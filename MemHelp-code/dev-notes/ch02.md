**翻车与返工（计划自审抓出的三个真问题）**

1. **测试里混进永真断言**：Task 3 的 `test_upsert_by_session_is_idempotent` 里有一行
   `assert sqlite_session.query(type(first)).count() if False else True` —— 我起草时的
   残渣，恒为真、测不出任何东西。已删掉，留下真正有判据的
   `assert sqlite_session.query(Conversation).count() == 1`。
   *根因*：起草时想写「查行数」但还没定下用哪个模型类，先用了个占位表达式，忘了删。

2. **`escape_like` 的归属自相矛盾**：我第一版写「放在 `app/db/repositories.py`，或放在
   `app/tools/schemas.py`，二选一并写进注释」——**一个「二选一」的指令就是让实现者
   去猜**，这正是计划自审第 2 项要抓的。而且我把它和 `tools/knowledge.py` 的职责搞混了：
   工具层不该负责拼 SQL 转义。
   *修法*：确定归属 —— `escape_like` 定义在 `app/db/repositories.py`，**只被
   `FaqRepository.search` 调用**；`tools/knowledge.py` 把 keyword 原样传下去。
   相应地，Task 6 的测试从「断言工具层转义」改成「断言工具层**不**重复转义」
   （重复转义会把 `100%` 变成 `100\\%` 再变成 `100\\\\%`，反而查不到）。

3. **测试调用未定义的函数**：Task 8 的 `test_error_text_is_redacted` 调用了
   `redact_result_error`，而 Interfaces 里从未定义过它。实现者只能自己发明一个，
   或者把它猜成 `app.errors.redact`。
   *修法*：改成通过**真实公开接口**断言 —— 构造一个 `error` 里带 `sk-...` 的
   `ToolResult`，断言 `to_tool_message_content(r)` 的输出里不含该密钥。
   顺带补了一条超大结果截断的测试（原本只在实现描述里提了截断，没有测试钉住）。

**这次自审的结论**：三个问题全是「实现者会卡住或会写错」的类型，没有一个是「打字错误」。
计划里最危险的不是写错函数名，而是**留下没定下来的选择**（问题 2）和**引用了不存在的东西**（问题 3）。

**翻车与返工（按根因分类）**

1. **`deepseek-flash` 是思考模型，`reasoning_content` 必须回传**（T9，最严重）
   - 端到端探针报 `400: The reasoning_content in the thinking mode must be passed back to the API.`
   - 根因：编排第 2 次调用时**重建**了 assistant 消息
     （`AIMessage(content="", tool_calls=[chosen])`），把 `additional_kwargs` 里的思考内容丢了。
   - 为什么它看起来像随机故障：**只在模型真的产生了思考内容时才炸**。单测全绿。
   - 修法：复用第 1 次响应那条消息，只裁剪多余的 `tool_calls`（`_first_call_only`）。
   - ch01 的结构化提取踩过同一个坑 —— 这是本项目第二次同类翻车。

2. **`monkeypatch` 在全量测试下静默失效**（T8）
   - `monkeypatch.setattr(executor, "get_tool", fake)` 单跑该文件全绿，全量跑 6 条红。
   - 实测证据（在 `execute_tool` 内部打身份）：
     `global_get_tool_is_module_attr=False` —— 即
     `execute_tool.__globals__["get_tool"]` **不是**
     `sys.modules["app.tools.executor"].get_tool`。测试隔离把模块加载了第二次，
     测试 patch 的是新模块属性，函数用的是旧 globals。
   - 修法：`execute_tool` 接受显式 `resolve` 参数，测试注入它，**不经过模块全局名**。
   - 我先后猜过三种原因（`-W` 标志、夹具拆卸顺序、`sys.modules` 重复），**三种都错**，
     只有插桩找到了真因。记下来是因为其中两种「修法」会碰巧让它变绿、然后在别处复发。

3. **SQLite 只对 `INTEGER PRIMARY KEY` 自增**（T3）
   - 报 `NOT NULL constraint failed: conversations.id`。
   - 修法在**模型**里：`BigInteger().with_variant(Integer, "sqlite")`。
     没有改成「测试里手工赋 id」——那样测的就不是生产类型了。

4. **`@tool` 包装层忘了 `await`**（收尾阶段才发现，见阶段 7）
   - 工具返回的是 coroutine 对象，模型复述出 `<coroutine object query_faq at 0x...>`。
   - 单测测不出来，因为假执行器不经过真工具。

5. **我自己的测试用例写错，反复三次**
   - `_common()` 收下了 `executor` 参数却**从没放进 kwargs** → 9 条用例静默跑了真执行器；
     表现是 `duration_ms==1`（而非 12）与 `executor.calls==[]`。
   - 一条永真断言 `assert X or True`（T1）—— 测不出任何东西，我自己的注释都写了「它不断言什么」。
   - `_reply_message` 里 chunks 分支判断用了 `reply != "ok"` 当哨兵，
     而 `"ok"` 正是默认值，无法区分「显式设成 ok」与「没设」→ 改用 `model_fields_set`。

6. **`Set-Content` 写坏编码，踩了三次**

**翻车与返工**
- 迁移脚本第一次执行前我先跑了 `--dry-run`，确认 13 条语句与顺序无误才真跑。
- 迁移对既有 2 行 seed 会话做了**回填**（`demo-seed-1` / `demo-seed-2`）而不是留 NULL。

**翻车与返工**

1. **`@tool` 包装层忘了 `await`**（端到端才暴露）
   - 现象：回答是「我帮你正在检索常见问题了：`<coroutine object query_faq at 0x...>`」。
   - 根因：`registry.py` 里 `query_faq` / `create_ticket` 写成同步函数直接
     `return _query_faq(...)`，而底层是协程函数 —— 返回的是 coroutine 对象，
     LangChain 把它当结果原样回灌。
   - 为什么单测全绿：假执行器**不经过真工具**，而注册表测试只检查名字/描述/Schema。
   - 修法：改 `async def` + `await`，并新增 `tests/test_tool_invocation.py`
     **真调**五个工具。破坏性验证过：去掉 `await` → 正好 3 条红 +
     `RuntimeWarning: coroutine 'query_faq' was never awaited`。

2. **`demo-ch02.ps1` 的 curl 用了 `-d '<json>'`**
   - 现象：三条验收「一个 SSE 帧都没有」，全 FAIL 且没有错误信息。
   - 根因：PowerShell 吃掉内联 JSON 的引号，curl 收到坏 JSON。
   - 修法：请求体写临时文件 + `--data-binary "@file"`（UTF-8 **无 BOM**）。
     这是 ch01 `demo.ps1` 早就用 `& curl.exe @args` 数组规避过的坑，我换了个写法又踩一次。

3. **`.Count` 在单元素上返回 `$null`**
   - 现象：`status` 帧其实有 1 个、`tools` 徽章其实有，却被判「没有」。
   - 根因：`Where-Object` 单元素时返回**对象**而非数组，`.Count` 得 `$null`。
   - 修法：一律 `@(...)` 强制成数组。同时修正 JSON 布尔比较
     （`ConvertFrom-Json` 把 `true` 转成 `[bool]`，写成 `-eq "true"` 会静默恒假）。

4. **评估集首跑 10/13，诊断后是两类不同的问题**
   - `acc1b` / `ticket1` / `ticket2`：用例**没给订单号却要求必调工具**，
     与行为约束 7「用户连订单号都没给就问快递到哪了，先问订单号，不要猜一个去查」**直接冲突**。
     这是**用例不现实**，不是模型选错 → 修用例（补上订单号）。
   - 修完 `ticket1/2` 仍红：模型在用户明确说「帮我建个工单」时去调了 `query_order`。
     这是**真实缺陷** —— 该执行动作时它去查数据了 → 按既定规则改**工具描述**
     （明确「用户要求建工单时直接调本工具，不要先查订单」），**没有改判定标准**。
   - 结果 14/14。

5. **`edit` 工具会静默丢掉 `.ps1` 的 UTF-8 BOM**（第三次同类翻车，已根治）
