## 阶段 1 · brainstorm 定稿（2026-10-25）

### 用户关键原话

- 「我要用 Superpowers 模式给客服系统训练一个自己的模型:微调一个多标签主题分类器,把飞轮攒下的低置信度问题按主题批量归类,好决定先补哪块知识。F:\DeepSeek-Harness\memhelp-code-myself\MemHelp-code\sql中有ch10的sql语句」
- 功能需求 1–6 全文：数据处理四步（清洗 / 归并术语表 / 分层抽样 80/10/10 / 数据增强只扩训练集）、多标签标注「一句话字面提到几个诉求就打几个标签,一个不多一个不少」、RoBERTa-wwm-ext 全参微调不用 LoRA、按类目 P/R/F1 + 每类混淆矩阵 + 人工抽错复核、旁路批量推理写 `topic_classifications`（实时主链路不调它）、主题分布页。
- 17 类与近邻边界原话：「退换货、物流、尺码、发票四大类领头」「修归保修维修、退归退换货;运费管钱、物流管货;价保是补差价、优惠活动是券和满减」。
- 技术栈钉死：「哈工大讯飞 RoBERTa-wwm-ext,全参微调」「推理服务化(如 ONNX / transformers 服务)」；本章不做：LoRA/QLoRA、embedding 微调、意图识别微调。
- 工作要求：「全程走 Superpowers 流程,技能自动触发;产出不是可单测代码的任务(纯 Prompt、数据类、训练类),把 TDD 那步换成拿标注样例或评估集跑一遍验证」「前端部分是例外,用 Vibe Coding 方式直接做」「涉及具体库、框架、API 的用法……一律先用 Context7 MCP 查最新官方文档和接口定义再动手」「上面点名的技术选型是定死的,实现中发现矛盾或走不通,停下来问我」。
- 三个决策答复：测试集 gold → 「我先逐条人工标注测试集,你再抽审至少 30 条」；批跑触发 → 「后台按钮 + 脚本手动触发,带水位提示」；服务形态 → 「B — 独立旁路推理服务」。
- 分节设计六轮全部「认可」：§1 类目表与数据流水线 → §2 训练 → §3 评测 → §4 推理服务与落库 → §5 前端 → §6 接缝。

### 关键产出

- 仓库勘察（真实数据，非推断）：
  - `sql/ch10-ddl.sql` 已存在但 **untracked**；`topic_classifications` 表**已在 MySQL 建好、0 行**，带 `UNIQUE uk_question_id` + 外键指向 `low_confidence_questions(id)` → 重跑是覆盖不是追加。
  - `low_confidence_questions` **只有 27 行**（retrieval_low_conf 15 / self_check 7 / user_feedback 5），含重复文本，去重后 **12 条唯一**。
  - 现有 KB 类目与 17 类不同源：`knowledge_chunks.category` 是「对话挖掘 / 售后手册 / 商品 FAQ / 商品与配送 / 退货政策 / 商品型号手册 / 物流 / 账务」（48 行），`faq.category` 只有售后/物流/账务（6 行）→ 17 类必须自建。
  - `app/db/models.py` 现有 12 个 ORM 模型，`tests/test_db_models.py:13 test_metadata_has_exactly_twelve_tables` 钉住表集合 → ch10 要改成 13 表。
  - 静态页挂载模式在 `app/api.py:2294-2362`（每个子页 redirect + `StaticFiles(html=True)` 挂载），现有 `/chat`、`/rag-eval`、`/review`、`/eval-trend`、`/observability`；`web/` 纯静态无构建步骤。
  - 硬件：RTX 5060 Laptop **8151 MiB，驱动 573.24，sm_120** → torch 必须 cu128；当前 `.venv` **没有 torch/transformers/onnx**。
- 环境实测（关键，改变了设计前提）：
  - `huggingface.co`、`hf-mirror.com`、`download.pytorch.org/whl/cu128`、`pypi.org` **全部可达**；cu128 有 torch **2.7.0–2.9.1 的 win/cp312 轮子**。
  - `hfl/chinese-roberta-wwm-ext` 的 config：`BertForMaskedLM`、12 层、hidden 768、vocab 21128、**无 id2label** → 用 `AutoModelForSequenceClassification(num_labels=17)` + `BertTokenizer`，不是 RobertaTokenizer。
- 设计文档：`docs/superpowers/specs/2026-10-25-ch10-topic-classifier-design.md`（11 节 + 20 项决策 D1–D20）。
- 关键决策：17 类 sigmoid 多标签（softmax 结构性做不到多命中）；独立 sidecar 8100 无状态不连库、主应用零 torch（测试钉住）；批跑编排单份 `run_batch()` 供 API 与脚本共用；便携 upsert（兼容 SQLite 测试）；labels 直接存中文类目名；「其他」独占且空预测兜底 `["其他"]`；阈值只在 val 扫、测试集只报数；真实 12 条只进 test；混淆矩阵用纯 HTML/CSS（避 matplotlib 中文字体坑）。

### 被拒绝 / 纠偏

- 用户否掉「单进程内嵌」（方案 A），选独立旁路 sidecar：实时链路真的碰不到模型，ML 依赖出问题不会拖垮 ch09 的对话服务。
- 用户否掉「定时器自动批跑」，选手动按钮 + 脚本 + 水位提示：少一个无人看管的失败面。
- 用户否掉「B + ONNX 导出」，只保留 transformers 服务：ONNX 多一层导出与数值一致性校验，多一块返工面，需求原文允许二选一。
- 用户否掉「测试集用大模型预标、只报一致率」，选我逐条人工标注 + 抽审：训练数据是模型造的、标签也是模型预标的，测试集再用模型标，F1 只是两个模型互相认同。
- 用户否掉「混淆矩阵上前端页」：评测是研发视角（一次看一次），主题分布是运营视角（天天看），混在一页两边都难看。
- 自我纠偏（我自己在问之前就改了主意并说明理由）：`pos_weight` 先不加 —— 会和每类阈值扫描混在一起，说不清是哪个在提分。

### 翻车与返工

- **网络探测假阴性浪费一轮**：先用 `Test-NetConnection` + `Invoke-WebRequest` 探测，得出「pypi.org / huggingface.co / download.pytorch.org 全不可达」的错误结论。真因是 PowerShell 5.1 默认 TLS 版本低 + `Invoke-WebRequest` 报「基础连接已经关闭: 接收时发生错误」。改用 venv 里的 Python `urllib` 重探，**五个站点全部 200**。教训：在 PS 5.1 上判断 HTTPS 可达性不能用 `Invoke-WebRequest`。
- 一次工具调用写坏（把 ACP 标签当工具名发出），无副作用，重发即可。
- 需求与现状的硬冲突（不是我的错，是需求前提）：需求说「语料从飞轮低置信度问题池捞真实问题」，实际池子里只有 27 行 / 12 条唯一 —— 真实语料规模支撑不起训练，**造数从「补足」变成「主力」**。这个事实已写进 spec §1.1 与 §5.2，避免日后误以为模型主要是真实数据训出来的。

- 任务顺序（依赖链）：T1 环境 spike → T2 类目表 → T3 清洗 → T4 分层 → T5 增强 → T6 合成语料与预标 → T7 流水线 CLI → **T8 测试集人工标注（唯一强制用户参与）** → T9 ORM/仓储 → T10 训练 → T11 评测 → T12 推理阈值化 → T13 sidecar → T14 批跑/路由/CLI → T15 前端页 → T16 回归收尾。
- 动手前按需求 3 查了 Context7 四处，均记录在计划里：
  - FastAPI：`@asynccontextmanager` + `FastAPI(lifespan=...)` 是当前推荐写法，`startup`/`shutdown` 事件已弃用；`@app.exception_handler`。

  - uv：torch 走专用索引的官方写法是 `[[tool.uv.index]] name=... url=... explicit=true` + `[tool.uv.sources] torch = { index = "pytorch-cu128" }`。
- 计划自审改了 3 处（写进计划末尾「自审」段）：①spec §9.2 的测试清单漏了训练与评测两块，按「能被单测的最小粒度」补 `app/topics/training.py` 与 `app/topics/evaluate.py`，属对 spec 的补充而非偏离；②「测试集人工标注」不能压成抽象步骤，拆成独立 Task 8 并排在训练之前；③前端保持 Vibe Coding，只留一条「页面不是 404」的冒烟断言。

### 被拒绝 / 纠偏

- 执行方式我给了两个选项并推荐 Native（16 个任务的接口已在计划里写死，且 T1/T6/T10 要真跑 GPU、T8 要我逐条标注、dev-notes 的「用户关键原话」只有本会话有）—— 用户选 Native，与推荐一致。
- 计划里给 transformers 留了退路：装最新 v5（5.20.2）跑 smoke，若 `problem_type` 或 `BertTokenizer` 被改签名就锁 `>=4.57,<5`。这不是换选型（仍是 RoBERTa-wwm-ext 全参微调），只是版本兼容处理，故未单独打断用户询问。

### 翻车与返工

- **Context7 查 transformers 没查到点子上**：`query-docs` 对 `/websites/huggingface_co_transformers_main` 连查两次，返回的全是 LayoutLMv2 的 `config` / `forward` 文档，没命中文本分类任务页。结论只能降级为「config 有 `problem_type` 字段」，真正的 API 行为改由 T1 的实跑 smoke 验证。教训：Context7 对 transformers 这种超大文档库召回不稳，**关键 API 必须用最小脚本实跑确认**，不能把文档片段当结论。
- **`transformers` 已是 5.20.2 大版本**：此前按记忆里的 4.x 写设计，计划阶段查 PyPI 才发现。v5 的 `Trainer` 与部分 tokenizer 类有改名，故计划里把「实跑 smoke」提前到 T1，并把版本退路写死。
- 计划初稿把「训练脚本」和「训练循环」都塞进 `scripts/train_topics.py`，自审时否掉：训练循环是本章最需要单测的代码，放脚本里单测粒度就退化成端到端。改为 `app/topics/training.py` + 薄脚本。

## 阶段 3 · 任务执行（2026-10-25）

### 用户关键原话

- 执行方式：「Native：我自己按计划逐任务执行（推荐）」。

### 关键产出

**T1 环境 spike（把版本返工点提前撞掉）**

- `uv sync --extra ml` 装成：`torch==2.9.1+cu128`、`transformers==5.20.2`、`safetensors==0.8.0`、`huggingface-hub==2.3.0`、`tokenizers==0.23.3`。torch 下载 2.7GiB，全程 11 分 24 秒。
- GPU 实测：`2.9.1+cu128 True (12, 0)`，`torch.randn(64,64,device='cuda')` 的 matmul 出有限值 —— **sm_120 的 kernel 可用**，不必退 CPU 版。
- 多标签 API 实测（**transformers 5.20.2 下全部可用**，无需锁回 v4）：
  - `AutoModelForSequenceClassification.from_pretrained(..., num_labels=17, problem_type="multi_label_classification")` 被接受，`config.problem_type` 回读一致；
  - `BertTokenizer.from_pretrained` 正常，`vocab 21128`、`do_lower_case True`；
  - 12 层 / hidden 768 / **102.3M 参数**；classifier 是新初始化的（`MISSING: classifier.weight/bias`，符合预期）；
  - 前向 `logits (2, 17)`；bf16 autocast 下 `dtype bfloat16`、形状不变。

### 被拒绝 / 纠偏

- **计划里 T2 的断言「每个类目名必须出现在自己的边界说明里」被我改掉了**：17 类里 6 类的边界说明本来就没重复自己的名字（如「货的运输状态。「钱」归运费」），这条断言会把合格的类目表判红。改成断言**三组近邻双向提及**（退换货的边界提到保修维修、物流提到运费、价保提到优惠活动及其反向），这才是需求真正要求的东西。
- **HF 缓存不走默认位置**：不改配置硬试、也不请求放宽沙箱，而是让训练与推理全部指向 `models/pretrained/chinese-roberta-wwm-ext` 本地快照。

### 翻车与返工

- **HF 缓存目录写不进去**：`BertTokenizer.from_pretrained("hfl/...")` 在 `C:\Users\dbq\.cache\huggingface` 报 `PermissionError: [WinError 5]`。改 `HF_HOME` 到工作区 `.hf-cache` 后仍然失败，但失败点变成 huggingface_hub 自己在 `snapshots/<hash>/tmpXXXX/dummy_file_src` 上 `os.open` —— 说明不是「没有写权限」（同一目录下 `New-Item`/`Set-Content` 都成功），而是它那套「建临时目录→探权限→move」的流程在本沙箱里走不通。
- 绕法：改用 `snapshot_download(..., local_dir=models/pretrained/chinese-roberta-wwm-ext)` 直接落进工作区，不经缓存符号链接。6 个文件 1 分 37 秒下完。后续训练脚本一律吃本地目录，配 `HF_HUB_OFFLINE=1`，不再碰仓库 id。
