## 阶段 1 · brainstorm 定稿（2026-10-24）

### 用户关键原话

- 「我要用 Superpowers 模式给客服系统装上眼睛,再把答不上的问题变成改进燃料。sql文件夹有ch09的sql语句.」
- 功能需求 1–6 全文：Langfuse 全链路 / 意图维度 token 成本 / 三入口入池带召回快照 / 飞轮流水线（标准化、查重、review_queue、审核落库）/ 自动化评估趋势 / 审核后台。
- 技术栈钉死：「Langfuse:开源、自部署,链路数据不出自家服务器」；「本章不做：低置信度问题按主题归类的微调分类器」。
- 工作要求：「涉及具体库、框架、API 的用法……一律先用 Context7 MCP 查最新官方文档」「上面点名的技术选型是定死的,实现中发现矛盾或走不通,停下来问我」。
- 「给你权限,你来帮我完成这个docker容器的问题吧,我现在已经启动了一个mewhelp的容器.你来帮我继续完成」—— 授权我直接用 Docker 起 Langfuse。
- 设计评审选择：「批准，进入写计划」；校准兜底选择：「退回 ch05 阈值闸并写报告」。

### 关键产出

- 上下文勘察：主链路 `RagPipeline.retrieve_only()` 不调自评；ch04 的 `self_check` 落池只在旧 `app/chat_tools.py` 路径；`app/agent/graph.py` 的 `_confidence_gate` 是 ch05 最简阈值版；👎 只在 `web/app.js` 写 localStorage；`messages.citations` 不含分数。
- Context7 + 实测核对：
  - Langfuse 自部署 v4（web + worker + Postgres + ClickHouse + Redis + MinIO）已拉起，`http://127.0.0.1:3000`，server 4.69.0。
  - `langfuse==5.0.4`：`from langfuse.langchain import CallbackHandler`；trace 级属性用 `propagate_attributes(tags=..., metadata=...)`。
  - Metrics API v2 **不支持 `metadata.*` 维度**（400），但支持 `tags` → 意图成本改用 `tags=["intent:<x>"]` 聚合。
  - `compile(...).with_config({"callbacks":[...]})` 仍返回 `CompiledStateGraph`，`aget_state` / `checkpointer` / custom stream 全保留（四个探针脚本在 `scripts/spike_*.py`）。
- 设计文档：`docs/superpowers/specs/2026-10-24-ch09-observability-flywheel-design.md`（15 项决策 + 数据模型 + 测试策略）。
- 关键决策：主图在闸通过后补 `SufficiencyJudge` 自评入口；三入口入池都带 `retrieved_chunks` 快照；飞轮同步处理；置信度闸用三特征逻辑回归 + ch04 评估集留一法校准，LOO balanced accuracy < 0.70 就不发布模型、退回 ch05 阈值闸。

### 被拒绝 / 纠偏

- 用户否掉「异步飞轮」（先入池、后台再标准化），选同步：刷新审核页立刻可见；代价是每轮多 1–3 秒。
- 用户否掉「校准不达标也硬上模型」，选退回阈值闸 + 报告说明。
- 自我纠偏：不能直接改 `retrieve_only` 加阈值逻辑 —— 它在低分时返回空证据，Top1/Top2 分差与有效证据数就没了；改为新增 `retrieve_for_gate()`，旧接口保留给工具路径与既有测试。
- 自我纠偏：意图成本不能按 `metadata.intent` 聚合（实测 400），必须用 tags；trace 详情里仍保留 `metadata.intent` 供排查。

### 翻车与返工

- 沙箱里 `docker ps` 报 `Access is denied ... dockerDesktopLinuxEngine`；用户授权后切 `danger-full-access` 才连上 Docker。容器起来后策略已切回 `workspace-write`。
- Langfuse v4 的 `/api/public/v2/traces` 与 `/api/public/v2/observations/{trace_id}` 都是 404（events_only）—— 浪费一轮试错，最终按 observations v2 + metrics v2 设计。
- Metrics API 用 `dimensions=[{"field":"metadata.intent"}]` 被 400 拒绝，才改成 tags 方案。
- 四个探针脚本是一次性投入；交付前删除，避免仓库里留垃圾（m00504 后已提前删除）。

## 阶段 1b · 改用 Langfuse Cloud（2026-10-24）

### 用户关键原话

- 「我现在不再想自行部署 Langfuse，请先删除之前在 Docker Desktop 上下载的 Langfuse 相关 Docker 容器。我已在 .env 环境中配置好 Langfuse 云端连接信息，请据此完成相应的配置清理与调整，并检查 .env 中的云端配置是否完整可用。完成这些处理后，先输出一份计划供我评审，再让我选择执行方式，在我确认前不要实际执行变更。」

### 关键产出

- Docker 清理：`docker compose -p mewhelp-langfuse down -v --rmi all --remove-orphans`，删除 6 个容器（web/worker/postgres/redis/clickhouse/minio）、网络与 5 个卷、6 个镜像；`docker ps -a` 已无 langfuse 残留。
- 仓库清理：`git rm` 掉 `deploy/langfuse/`（compose 与 .env.example）与四个 `scripts/spike_*.py`；本地 `deploy/langfuse/.env` 一并删除，工作区不再保留自部署文件。
- `.env` 云端配置检查（不打印密钥）：`LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` 均 42 字符，`LANGFUSE_BASE_URL=https://jp.cloud.langfuse.com`；`GET /api/public/projects` 返回 200，项目 `My Project`、组织 `dbq's Organization`。三项齐全且鉴权可用。
- spec 已同步：D1 改为 Langfuse Cloud，§5.1 的 base URL、验收 1 的登录地址、§14 交付物同步改；本地部署相关描述清除。

### 被拒绝 / 纠偏

- 用户否掉自部署方案：Docker 容器/镜像全删，ch09 不再交付 compose 文件，也不再用 `127.0.0.1:3000` 验收。
- 之前基于本地 v4.69 的部署结论（端口、容器健康检查）作废；SDK 5.0.4 用法、`propagate_attributes`、tags 维度、编译期回调的结论仍然有效。
- 用户要求「先输出计划供评审，确认前不执行变更」——清理完成后暂停，不写任何 ch09 实现代码。

### 翻车与返工

- PowerShell `Invoke-WebRequest` 访问云端报「基础连接已经关闭」，设 TLS 1.2 后仍失败；改用项目 venv 的 `httpx` 验证成功（200）。验收脚本统一用 Python httpx，不依赖 PS 的 TLS 栈。
- 清理后本地无 Langfuse 可看，验收第 1 条改为登录云端项目；演示脚本不假设本机有 Langfuse 服务。
