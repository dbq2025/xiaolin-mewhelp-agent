## 阶段 1 · brainstorm 定稿（2026-10-24）

### 用户关键原话

- 「我要用 Superpowers 模式把客服系统的工具层从几个写死的内置工具,升级成即插即用的工具系统。sql文件夹有新增的ch08.sql文件.」
- 功能需求 1–7 全文（注册中心 / 参数校验 / 权限控制 / 执行引擎 / 审计 / MCP 接入 / 建工单确认流），技术栈钉死：MCP 官方 Python SDK + Streamable HTTP、LangChain 官方 `MultiServerMCPClient`。
- 「本章不做」：Skill 机制、仓储等更多外部系统。
- 工作要求：「涉及具体库、框架、API 的用法……一律先用 Context7 MCP 查最新官方文档」「上面点名的技术选型是定死的,实现中发现矛盾或走不通,停下来问我」。

### 关键产出

- 勘察结论：现有 5 个内置工具在 `app/tools/registry.py`（闭包工厂），校验在 `app/tools/schemas.py`（Pydantic，`extra="forbid"`），执行在 `app/tools/executor.py`（`execute_tool` 永不抛、`ToolResult` 契约）；`app/agent/tools.py` 目前**永远剔除 `create_ticket`**；图里 `interrupt()` 只在 `refund_await_order` 用过（ch06 订单选择器）。
- Context7 + 官方源码核对：`langchain-mcp-adapters 0.3.2` 的 `pyproject` 要求 `mcp>=1.24.0,<2.0.0`；`mcp` 2.x 把 `FastMCP` 改名 `MCPServer`，所以**必须钉 1.x** 才能用 `from mcp.server.fastmcp import FastMCP`。
- 设计文档：`docs/superpowers/specs/2026-10-24-ch08-tool-ecosystem-design.md`（本次新建，状态：定稿）。
- 三项选择经用户确认：
  1. MCP 清单**每轮对话前刷新**（不加 TTL，验收 3 立即生效）；
  2. 建单成功回复直接用 `create_ticket` 返回的 `message`（不再调模型）；
  3. 整体方案（统一注册表 + jsonschema 校验 + 写操作确认闸 + 审计 + 两个 MCP Server + 工单预览节点）照此推进。

### 被拒绝 / 纠偏

- 无用户否决。用户在三选一里选了「每轮刷新」「message 直出」，否掉了 TTL 缓存与「回灌模型再生成」两个备选。
- 自我纠偏：`query_logistics` 必须从 `schemas.py` / `registry.py` / `TOOL_NAMES` / `TOOL_LABELS` 全量删除，不能只从绑定列表里去掉，否则 `TOOL_NAMES` 自检与前端标签会留下孤儿。
- 自我纠偏：ch05 的 `/api/actions/create-ticket` 必须保持原样，只加 `confirmed=True`（按钮即确认），不改路由语义。

### 翻车与返工

- 小翻车：第一轮 `uv run` 因 `UV_CACHE_DIR` 指到用户目录被沙箱拒绝（`Failed to initialize cache ... 拒绝访问`）。改用工作区内 `F:\DeepSeek-Harness\memhelp-code-myself\.uv-cache` 后正常。
- 返工：`langchain-mcp-adapters` 最新版依赖 `mcp<2`，差点按 2.x 文档写 `MCPServer`；已按 1.x 的 `FastMCP` 定稿，待装包后再实测一次签名。
- 过程偏差（如实记）：先发了三选一确认、后补设计正文；用户已确认，正文与选项一致，未产生返工。
