## 阶段 0 · 立项、仓库勘查与流程分类

**用户关键原话**

> 「我要用 Superpowers 模式把客服系统里占位的分流器做成正式版,这是 Workflow 里最关键的节点。」
> 「指代消解:用 LLM 结合对话历史,把「它能退吗」这种带指代的话补全成一句不依赖上下文也能看懂的完整问题;问题本身已完整、指代已明确的,原样透传,不强行改写」
> 「Query 改写:口语模糊问法归一成标准问法,和指代消解一并处理」
> 「Query 扩写:把一句问题泛化成多条侧重点不同的检索查询(强制 JSON 输出,字段就 queries 一个数组),几条一起检索再去重合并;只对退款退货、售后这类高频、容错低的核心场景做,简单 FAQ 不扩;扩写放检索侧现查现用,库里知识只留一份,不在入库侧拆存多份」
> 「意图识别用 LLM prompt 路线,不训分类模型,prompt 按四件套写」
> 「分流精化:退款退货和售后走一条确定性子流程——先拿订单数据、再做 Query 扩写并强制检索政策条款,最后只把「这一单能不能退」交给主力 Agent 判断」
> 「槽位处理:缺订单号不让模型猜,执行阶段弹订单选择器让用户点选回填;退款原因不追问,用户提交退款单时从固定类目里自选;需求澄清留在主力 Agent 里做,意图识别只判「要干什么」」
> 「前端配套:订单选择器做成聊天流里可点选的订单卡片,点选后自动回填、流程接着走;退款单是一个简单表单,退款原因从固定类目里下拉选」
> 「无新增组件,延用现有聊天上游;意图识别默认配够格的大模型先把准确率做上去,成本吃紧时再走降级路」
> 「本章不做:微调小模型 / BERT 做意图分类;跨会话记忆」
> 「全程走 Superpowers 流程,技能自动触发;产出不是可单测代码的任务(纯 Prompt、数据类),把 TDD 那步换成拿标注样例或评估集跑一遍验证,其余步骤照走;前端部分是例外,用 Vibe Coding 方式直接做」
> 「过程留痕:在仓库 dev-notes/ch06.md 里追记开发过程…不许收尾时一次性补记」
> 「涉及具体库、框架、API 的用法…一律先用 Context7 MCP 查最新官方文档和接口定义再动手」
> 「上面点名的技术选型是定死的,实现中发现矛盾或走不通,停下来问我,不要自行换方案」

**关键产出**

- **流程分类：architectural**（替换分流子系统：coref、意图、退款确定性子流程、
  多查询检索、interrupt/resume、SSE 协议与前端卡片/表单，并改动 ch05 的图结构与契约）。
  已在对话中当面向用户宣布分类，允许其推翻。
- **仓库基线勘查（读代码，不靠记忆）**：
  - ch05 已留下 `app/agent/coref.py`（纯透传）、`app/agent/intent.py`（七类简单 prompt +
    启发式）、`app/agent/graph.py`（knowledge/business/complaint/chitchat 四出口）。
  - 业务工具 `query_order` / `query_product` / `query_logistics` 是**按编号确定性派生演示数据**，
    没有 orders 表，也没有「用户→订单列表」归属关系。
  - 退款单没有独立表；`tickets` 有 `ticket_type/description/idempotency_key`，可复用。
  - 检索侧已有 `RagPipeline.retrieve_only(query)`；扩写应加多查询合并入口，而不是改造入库链路。
  - SSE 契约现有 `meta/status/token/tools/citations/done/error`；前端在 `web/app.js` 按帧解析。
  - 当前 `.env` 上游为 DeepSeek 兼容端点，`OPENAI_MODEL=deepseek-flash`。
- **关键澄清（用户已选）**：订单选择器按 session 派生 3 张演示订单，退款单复用 `tickets`；
  不新增 orders / refund_requests 表。用户选择 A。
- **Context7 与真机探针（先查后写）**：
  - Context7 `/websites/langchain_oss_python_langgraph`：HITL 用 `interrupt(value)` 暂停，
    `Command(resume=...)` 恢复，同一 `thread_id` 复用 checkpointer。
  - 本机 `langgraph 1.2.15`：`Command(*, graph=None, update=None, resume=None, goto=())`；
    `interrupt(value, *, response_schema=None)`。
  - 真机探针（`astream(stream_mode="custom")`）：节点内 `get_stream_writer()` 发
    `order_picker` 后 `interrupt()`；`astream` 结束得到 `snapshot.next == ("await_order",)`，
    `snapshot.tasks[0].interrupts[0].value` 为中断载荷；`Command(resume=...)` 能从暂停点续跑，
    节点内 token 事件正常。结论：可用 interrupt/resume，不需要自建 pending 状态机。

**被拒绝或纠偏**

- 主动排除的方案：
  1. 让主力 Agent 在对话里追问订单号 —— 违背「缺订单号不让模型猜、执行阶段弹选择器」；
  2. 自建 pending 槽位 + 重新进图 —— 等于手写一套中断恢复，checkpoint/幂等返工面大；
  3. 新增 orders/refund_requests 表 —— 用户在本阶段明确选 A（演示订单 + 复用 tickets）。
- 没有擅自把 `after_sales` 留在 business：用户明确要求退款退货与售后同一条子流程。

**翻车与返工**

- 暂无代码改动。已提前说明风险：当前模型是 `deepseek-flash`，若评估集显示指代/意图
  不达标，会停下来把结果交给用户决定是否配更强的 `INTENT_MODEL`，不自行换模型。
