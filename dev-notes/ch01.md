### 最大的一个坑：FastAPI 原生 SSE 满足不了「一个路径两种响应形态」

计划里（spec 第 7 节）写了用 astapi.sse.EventSourceResponse，并预留了「无此模块就退回手工拼帧」的方案。实际执行下来发现：**模块在，但用不了**，我做了四组最小对照实验才定位清楚：

1. esponse_class=EventSourceResponse + yield ServerSentEvent → 正常（	ext/event-stream，帧格式规范）。这条没问题。
2. 手工构造 EventSourceResponse(...) 再 eturn → Starlette 把它当普通内容二次编码，报 'ServerSentEvent' object has no attribute 'encode'。
3. 让路由是**普通 async 函数**、内部 eturn 一个异步生成器（想借此同时支持 JSON 分支）→ FastAPI 拿到的是未 await 的协程，响应体为空。
4. 拆成**两条同路径路由**、各自用 guard 依赖分流 → 不行：Starlette 匹配到第一条「路径+方法」相同的路由就结束，guard 里抛 HTTPException 只会直接返回 422，**不会回落到第二条**。两种注册顺序都试了，必然有一半请求拿到 422。

结论：原生 SSE 只支持「路由函数本身是异步生成器」且只认 ServerSentEvent（yield 字符串会被编码成 data: "..."，yield Response 会被当成数据序列化）。

**最终方案**：退回计划预留的 fallback —— 普通 StreamingResponse + 自己编码 SSE 帧。编码逻辑抽成 pp/sse.py::sse_frame（纯字符串处理），用 5 条测试单独钉住格式（帧结构、空行结尾、中文不转义、换行不撑破帧、data 是合法 JSON）。同时把「非流式」分支放在**路由函数里**直接 await 并返回 JSONResponse，这样上游错误发生在响应开始之前，能被 UpstreamError 处理器正常映射成 502/503。

**代价与收益**：代价是帧格式正确性要自己保证（已用测试兜住）；收益是 API 契约与三条验收标准**完全没变**。
